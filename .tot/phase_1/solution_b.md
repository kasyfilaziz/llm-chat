# Problem

Lumina requires a Phase 1 implementation connecting a Dioxus UI, a SQLite database, and a streaming OpenAI-compatible API. The user, a Senior Data Engineer, needs a robust way to synchronize state across these three boundaries without dropping tokens or freezing the UI.

# Assumptions

1. The user's background in Data Engineering makes them highly averse to data loss or silent state drift.
2. The SQLite database is fast enough on modern SSDs that synchronous (or near-synchronous) writes will not noticeably degrade user experience.
3. The UI exists solely to reflect the true state of the system, which lives on disk.

# Solution Summary

The SQLite Source-of-Truth (Database-First). Every action is written to the database first. The UI acts as a dumb, read-only projection. Streaming LLM tokens are written sequentially to the database, and the UI polls or listens for database changes to re-render.

# Detailed Implementation

**Step 1: The Core DB Engine**
Create a robust `rusqlite` layer. Implement functions for `insert_message`, `update_message_content` (for streaming tokens), and `get_messages_for_conversation`.

**Step 2: The Flow**
When the user clicks "Send":
1. The UI blocks momentarily to write the user's message to SQLite.
2. The UI reads from SQLite and updates its local signal to render the new message.
3. The UI spawns an async network task.

**Step 3: The Network Stream**
1. The HTTP client requests the streaming response from the OpenAI API.
2. **Crucial Difference**: As every 5-10 tokens arrive, the network task executes a SQL `UPDATE` to append the new text to the database record.
3. After the SQL `UPDATE` succeeds, it sends a lightweight notification (or the UI simply polls SQLite every 100ms) to force Dioxus to re-query the database and re-render.

# Consequences

## Positive Outcomes
- **Bulletproof Integrity**: If the app is force-closed or the power goes out mid-stream, the exact partial sentence generated by the LLM is perfectly preserved in SQLite.
- **Simplified UI**: The Dioxus components contain almost zero business logic. They simply `SELECT * FROM messages` and render.

## Risks & Failure Modes
- **I/O Bottlenecks & Jitter**: Running a SQL `UPDATE` for every single token (or chunk of tokens) causes massive disk I/O. If SQLite locks the database (since it's a single file), the UI will stutter heavily, destroying the "snappy" feel.
- **WAL Mode Required**: You must enable SQLite WAL (Write-Ahead Logging) mode, otherwise concurrent reads (the UI) and writes (the streaming token updater) will deadlock.

## Second-Order Effects
- To solve the I/O jitter, you will inevitably have to build a "debouncer" or "batcher" for the SQL updates, which drastically increases the complexity of the data layer.

# Verdict
This solution is best for users who prioritize absolute data integrity and crash-recovery over microsecond UI smoothness, and are comfortable tuning SQLite concurrency.
